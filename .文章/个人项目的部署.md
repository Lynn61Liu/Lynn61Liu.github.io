
把一个工作流复杂的 .NET 系统部署成 Demo 环境后，我学到了什么

**副标题**
一次看似只是“把系统跑起来”的部署任务，最后变成了关于隔离、调试、配置边界和工程判断的系统性训练。

## Context
在开发 NZAT workshop management system 的过程中，我需要把一个真实使用中的多服务系统整理成一个可以安全展示的 demo 环境。这个需求表面上看像是常见的“把应用部署到 Linux 上，再加几个容器”的任务，但实际做起来，我很快发现它并不属于那种可以靠一套默认模板快速套过去的场景。

原因很简单：这个系统本身不是一个轻量级展示型项目，而是一个工作流很重的内部运营系统。它有 React 前端、.NET API、PostgreSQL、Redis，也有很多围绕业务流程展开的状态管理、初始化逻辑和配置依赖。更现实的一层约束是，这台 Linux 主机上已经运行着多个其他项目，因此这次的目标并不是“找个空环境把它跑起来”，而是要在共享主机的前提下，为它设计出一个边界清晰、数据安全、可重复构建的 demo 环境。

我后来回头看，这其实已经不是一个单纯的部署问题了。它更像是在问我：当一个真实系统要从“内部使用”转成“外部可展示”的时候，我有没有能力重新理解它的运行边界，并把这些边界明确地表达在部署结构里。

## Problem
一开始我以为这次工作的核心是容器化和服务编排，但真正的难点很快就变得更具体，也更现实。

首先，demo 环境不能和现有业务数据混在一起。即使技术上可以复用同一个数据库实例，业务上也不能允许 demo 直接依赖真实数据，因为这会让测试、重置、脱敏和后续维护全部变得危险。其次，我不希望这套 demo 部署和主机上已有的容器运行方式互相干扰，尤其是在已经存在管理面板和既有运行习惯的情况下，新的环境越“显眼”，越容易给后续运维带来混乱。最后，前端、API、数据库、缓存、初始化逻辑之间的依赖链必须完整打通，否则就算某个容器“起来了”，系统也未必真正可用。

这意味着我要解决的不是“服务能不能运行”，而是“这个 demo 环境能否被稳定地解释、调试和维护”。这两者差别很大。前者更像一次技术操作，后者更像一次工程设计。

## Initial Approach
最开始，我采取的是一种很自然的思路：既然已有的系统镜像和基础服务都已经存在，那就尽量复用它们，再补一套独立的 demo 数据库，把新环境和已有项目一起部署在同一台主机上。这个思路的优点很明显，启动快、改动少，也符合很多工程场景下“先最小改动跑起来”的直觉。

但很快我就意识到，这个方案虽然高效，却不够完整。它默认假设 demo 环境只是 production 的一个简化副本，而没有真正考虑 demo 场景自己的诉求。一个可演示环境和一个真实业务环境，看起来都是“运行同一套系统”，但它们关注的重点并不一样。production 关心的是稳定性、连续性和业务正确性；demo 则更关心安全隔离、可重建性、可解释性，以及在出现问题时是否容易快速恢复。

这也让我开始重新审视自己的目标。我不是在复制一个系统，而是在为一个已有系统设计另一种运行方式。这个认识的变化，直接影响了后面所有技术决策。

## What Went Wrong
部署真正开始之后，隐藏的问题比我预想中暴露得更快，而且很多都不是那种“看一眼就知道答案”的错误。

第一个问题出现在运行时隔离层面。为了让这套 demo 环境不要和主机上已有的容器运行方式混在一起，我尝试使用 rootless Podman。这个选择本身没有问题，但它也意味着我不能再完全沿用之前对 Docker 网络和容器可见性的直觉。尤其是在 rootless 模式下，自定义网络和动态连接容器的行为并不总是像 Docker Compose 那样顺滑，这使得最开始的一些网络设计假设失效了。

第二个问题来自配置读取方式。我最初按常见习惯写了一套环境变量，以为应用会读取 `ConnectionStrings:DefaultConnection` 之类的配置键，但实际检查镜像内部的配置文件后才发现，这个 API 读取的是 `ConnectionStrings:Default`。这看起来只是一个小差异，但在真实部署里，小差异往往会变成很大的时间损耗，因为它会让你以为“配置已经传进去了”，但应用行为却完全不按预期走。

第三个问题来自数据库初始化。我原本希望通过空库加自动 migration 的方式，把 demo 数据库从零启动起来，这听起来是最干净、也最可控的方案。但真正运行后才发现，后续 migration 依赖了一个并不存在的 `jobs` 表。也就是说，这套 migration 链并不能在空数据库上完整地重建系统结构。它在某种程度上默认了数据库里已经有一套更早期的 schema 基线。这类问题在已有项目里并不少见，本地开发时很容易被已有数据掩盖，一旦切换到真正空白的环境，就会立刻暴露出来。

第四个问题是应用级启动依赖。即使 API 已经能连上数据库，启动流程仍然会因为 Redis 配置缺失、库存导入文件路径不存在、初始化服务需要预置数据等原因失败。也就是说，容器启动、数据库联通、migration 成功，这些还不足以说明“系统可以用了”。这个阶段我最大的感受是，一个工作流复杂的内部系统，真正的启动条件远远不只是“应用进程能跑”。

## Investigation & Debugging
整个过程中最有价值的，不是最后用了什么命令，而是调试思路的变化。

一开始我也有过那种很常见的冲动：看到报错就改一处配置，再重启一次；看到网络不通，就尝试换一条命令；看到容器起不来，就继续补一个环境变量。但真正让我推进下去的，不是这种“多试几次”的节奏，而是开始有意识地把问题拆成一层层可验证的链路。

我先区分了基础设施问题和应用问题。比如，如果宿主机 curl 不通，那优先看端口映射、容器状态和 Pod 层的网络；如果宿主机能通，但前端页面返回 502，那就说明问题不在容器有没有启动，而在 web 到 API 的反向代理链；如果 API 日志里显示 migration 运行了，但应用还是启动失败，那就说明问题已经上升到更高一层，进入了应用初始化逻辑本身。

接着我开始验证配置，而不是假设配置。我没有继续相信“这个 key 应该会被程序读取”，而是直接进入镜像查看 `appsettings.json` 和 `appsettings.Development.json`，确认程序真正使用的连接串名称和默认端口。我也没有只看 env 文件，而是检查容器实际拿到的环境变量，确认它们和预期是否一致。很多时候，问题不是“配置没写”，而是“配置写了但程序没用”。

数据库部分的排查也很关键。当自动 migration 在空库上失败时，我没有继续反复重启 API，而是把思路从“让 migration 自己修好”切换成“先验证 schema 基线是否完整”。最后我通过从现有数据库导出 schema 的方式，让 demo 库先拥有完整结构，再让 API 接着运行后续流程。这个调整本质上是在承认一个事实：理想中的初始化链路不一定真的适用于当前项目，而工程上更重要的是识别这个事实，而不是硬撑着让错误路径继续消耗时间。

最后，在 web 层我也遇到了很典型的问题：页面能够打开，但 API 请求返回 502。顺着排查后才发现，前端容器和 API 容器并不在同一个网络上下文里，Nginx 反代指向的 `127.0.0.1` 实际上指向的是 web 容器自己，而不是 API。这个问题再次提醒我，部署时“地址写得像对的”不等于“链路真的对了”。网络问题永远要回到具体的运行上下文里去验证。

## Technical Decisions and Trade-offs
随着问题一个个暴露出来，我的技术选择也逐渐从“方便”转向“更适合当前约束”。

我最终保留了 rootless Podman 作为 demo 环境的运行时，不是因为它比 Docker 更先进，而是因为这次的目标是隔离，而不是统一。主机上已经有多个项目在运行，我不希望 demo 环境继续进入现有容器管理视角里，更不希望它在运行时和已有项目混成一团。对这个场景来说，Podman 的价值不在于工具本身，而在于它提供了一种更清晰的边界。

数据库方面，我选择了把 demo 数据库完全独立出来。即使从资源利用的角度看，复用一个实例似乎更省事，但从 demo 环境的目标来看，能否被安全重置、能否导入脱敏数据、能否在出问题时快速销毁重建，远比“少开一个服务”更重要。这个决定其实体现了一种很实用的工程判断：不是所有节省资源的方式都值得保留，尤其当它会牺牲边界清晰度的时候。

网络层面，遇到 rootless 自定义网络不稳定后，我最终改用了 Pod-based 的方式，把 web、api、db、redis 放到同一个网络命名空间里。这个方案没有那么“漂亮”，但它很好地降低了系统复杂度。容器之间都通过本地地址通信，调试路径更短，网络问题也更容易定位。它不是理论上的最优设计，但在这台主机、这套运行时、这个部署目标下，它是最实际的做法。

前端访问方式上，我先接受了高位端口访问，而没有一开始就去做完整的域名和 SSL 接入。这个决定背后其实也是一个节奏问题：先让系统链路跑通，再让访问入口变优雅。很多工程上的拖延，都来自过早追求“完整形态”。这次我更清楚地体会到，临时方案不是问题，只要你知道它是临时的，并且知道下一步该怎么收。

## Refactor / Improvement
回头看这次部署，最大的变化并不是“容器终于全部跑起来了”，而是系统结构终于变得更容易解释了。

一开始我面对的是一堆看起来彼此相关、但边界并不清晰的服务和配置。部署过程走到后面，web、API、数据库、Redis、种子文件、迁移链、反向代理、访问入口，这些东西的职责开始逐渐分离出来。哪些是运行时层面的隔离，哪些是数据层面的隔离，哪些是应用初始化层面的依赖，哪些只是访问入口层面的配置，这些界限开始变得清晰。

我觉得这才是这次工作的真正成果。不是多了一套 demo 环境，而是我对这套系统“如何被运行”这件事的理解被重新梳理了一遍。部署结构从“几个容器能工作”变成了“一个边界清晰、可维护的环境设计”，这个变化本身就是一种重要的工程改进。

## Lessons Learned
如果要总结这次经历最重要的收获，我会说它让我重新理解了“部署”这件事。

以前我更容易把部署看成代码完成之后的一步收尾工作，或者一种偏运维层面的任务。但这次让我更清楚地看到，部署一致性会直接影响调试效率、维护成本、环境安全和团队协作。如果一个系统只能在某台开发机器上正常运行，却不能在新的环境里被清晰地重建，那它的工程质量其实是不完整的。

我也更明显地感受到，工作流复杂的内部系统和很多展示型应用不一样。它们通常带有很多隐含假设：某些表默认已经存在、某些缓存默认已经可用、某些初始化任务默认能够执行、某些导入文件默认已经放在特定位置。这些假设在本地开发时很容易被忽略，因为环境已经“习惯性地正确”了；但只要换到新环境，这些假设就会一个个显形。

更重要的是，我学到“隔离”从来不只是把服务拆成多个容器。真正的隔离包括运行时隔离、配置隔离、数据隔离、初始化行为隔离，以及运维可见性的隔离。如果这些边界没有被认真设计，一个所谓的 demo 环境很可能只是“看起来分开了”，但其实仍然和原有环境纠缠在一起。

最后，这次经历也让我更确认一件事：优秀的调试不是靠猜，而是靠逐步把隐藏假设变成显式证据。只要问题还停留在“我觉得可能是哪里错了”，就很容易陷入低效循环。只有当我开始一层层验证运行上下文、配置来源、网络路径和启动依赖，问题才开始真正收敛。

## What I Would Do Next
如果重新做这套环境，我会更早地引入 demo 专用配置，而不是在已有 production 假设上不断修补。我也会更严格地把敏感连接配置从镜像里剥离出去，让不同环境的边界从一开始就是显式的，而不是靠经验去记住它们。

在应用层，我会尽早补上环境校验机制，让像 Redis 配置缺失、导入文件路径不存在、migration 不完整这类问题在启动早期就能给出清晰提示，而不是等系统走到更深的初始化阶段才失败。这样不仅更容易调试，也更适合做长期维护。

在运维层，我会把这次的手工步骤尽量沉淀成可重复的部署脚本和健康检查流程。因为真正有价值的 demo 环境，不是“这次终于部署成功了”，而是半年后仍然可以被稳定重建、清楚解释，并且能让别人理解这个系统的工程设计。

## 结语
这次经历让我意识到，工作流复杂的系统在部署时，真正重要的不只是“能不能跑起来”，而是能不能把原本隐藏的假设变成清晰、可控、可维护的系统边界。

对我来说，这次搭建 demo 环境的过程并不是一次简单的部署操作，而更像是一堂关于工程判断的复盘课。它让我看到，真正值得写进作品集的，不只是我把系统部署成功了，而是我如何理解问题、如何调整方案、以及我从这些失败和修正中学到了什么。
