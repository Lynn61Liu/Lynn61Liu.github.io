System Overview

This project is best understood as a real workflow system rather than a standalone CRUD application. It turns everyday workshop operations into traceable digital records and gives the business a stronger foundation for automation, reporting, and future process improvement.

Problem

Paper-based processes made jobs, service history, purchasing, invoices, and follow-up communication harder to track consistently across day-to-day workshop work.

Approach

I helped design and build a React, TypeScript, and ASP.NET Core platform that digitises the workshop lifecycle and connects it to surrounding business systems.

Result

The platform reduces duplicate data entry, improves traceability, and creates a maintainable base for ongoing workflow automation and reporting.

Deep Dive Sections

The strongest story in this project is the movement from scattered operational activity to structured software workflows. These sections can grow over time as more implementation detail, screenshots, and lessons are added.

01

Workflow modelling

The system needed to represent workshop work as a series of connected operational states, not isolated screens. Customer records, vehicle information, jobs, WOF service records, invoices, purchase orders, and reminders all influence the same service lifecycle.

  • Separated UI state from business workflow status so the system can stay maintainable as features grow.
  • Designed around traceability: users should be able to understand what happened, what is next, and what data supports the decision.
  • Kept the workflow practical for internal users who need speed and clarity during repeated daily tasks.
02

Integrations

Workshop software becomes more valuable when it connects to the systems already used by the business. The project includes integration thinking across email, Xero, and internal operational data flows.

  • Used API-driven boundaries to keep external communication separate from core workflow logic.
  • Applied outbox-pattern thinking for more reliable operational messaging and integration behaviour.
  • Learned that integration-heavy systems need early attention to failure states, retries, and observability.
03

Deployment and testing

Because this project supports real operations, delivery and quality practices matter as much as the feature work itself. Docker-based workflows, GitHub Actions, Azure Container Registry, and Playwright tests help make the system more repeatable and safer to evolve.

  • Containerised application delivery supports more consistent deployment across environments.
  • Playwright coverage focuses on critical end-to-end journeys rather than only isolated interface checks.
  • The project strengthened my understanding of release discipline for production-minded internal tools.

Reflection

Current lesson

Real-world workflow software needs careful modelling before feature expansion. The hard part is not only building forms and tables, but deciding how business status, user action, and system records should relate to each other.

Trade-off

The system has to balance workflow flexibility with maintainable structure. Too much freedom can make the system hard to reason about; too much rigidity can make it fail real workshop needs.

Next iteration

Future improvements could include role-based dashboards, deeper reporting, stronger analytics visibility, and more automation around reminders, purchasing, and follow-up tasks.
